# ADR-0002: 프론트엔드 상태 관리 방식 선택

**상태:** 채택 (Accepted)
**작성일:** 2025-05-18
**작성자:** 수다 프로젝트
**관련 문서:** 00-vision.md, 01-requirements.md, ADR-0001-mobile-framework.md

---

## 1. 배경 (Context)

React 기반 수다 프론트엔드는 다음 두 가지 종류의 상태를 다뤄야 한다.

- **전역 상태** — 로그인 사용자 정보, JWT 토큰. 로그인 페이지·번역 페이지·기록 페이지 등 모든 컴포넌트에서 공유 필요
- **로컬 상태** — 웹캠 영상, 인식된 단어 시퀀스, 번역 결과, 로딩 여부 등. 각 페이지 내부에서만 사용

ADR-0001에서 React(웹) → React Native(앱) 포팅 구조를 채택했으므로, 상태 관리 방식도 React 생태계와 일관성을 유지해야 한다. 또한 6주 일정 내에서 학습 부담 없이 즉시 적용 가능해야 한다.

---

## 2. 결정 (Decision)

**React 내장 `useState` + `Context API`** 를 채택한다.

### 채택 이유
1. **전역 공유 상태가 인증 1가지뿐** — 과도한 상태 관리 라이브러리 없이 Context 하나로 해결 가능
2. **외부 패키지 불필요** — React 기본 내장 기능으로 번들 크기 증가 없음
3. **React Native 포팅 호환** — Context API와 useState는 React Native에서 동일하게 동작
4. **즉시 적용 가능** — 별도 학습 없이 6주 일정 내 구현 가능
5. **구조 단순화** — `useAuth()` 훅 하나로 모든 컴포넌트에서 인증 상태 접근, Q&A에서 설명 용이

---

## 3. 대안 (Alternatives Considered)

### 대안 A — Redux Toolkit

**장점**
- 강력한 Redux DevTools로 상태 변화 추적 용이
- 대규모 앱에서 예측 가능한 단방향 데이터 흐름
- 미들웨어(Thunk, Saga)로 비동기 처리 체계화

**단점**
- 보일러플레이트 코드(Action, Reducer, Selector)가 많아 초기 설정 비용 높음
- 소규모 프로젝트에 과도한 복잡도
- Redux 개념(불변성, dispatch, store) 학습 시간 필요

**미채택 사유**
전역 공유 상태가 인증 정보 1가지뿐인 규모에서 Redux는 오버엔지니어링이다. 6주 일정에서 학습 비용 대비 이점이 없다.

---

### 대안 B — Zustand

**장점**
- Redux보다 훨씬 간결한 API, 보일러플레이트 최소
- Hook 기반으로 React와 자연스럽게 통합
- 번들 크기 작음 (~1KB)

**단점**
- 외부 패키지 추가 필요 (`npm install zustand`)
- React 기본 기능이 아니므로 React Native 포팅 시 별도 확인 필요
- 팀원이 있을 경우 별도 학습 필요

**미채택 사유**
Context API로 충분히 해결 가능한 규모에서 외부 의존성을 추가할 이유가 없다.

---

### 대안 C — Recoil

**장점**
- 원자(atom) 단위 상태 관리로 세밀한 리렌더링 제어 가능
- React 철학과 유사한 선언적 API

**단점**
- Facebook/Meta 내부에서도 실험적 단계로 유지, 생태계 불안정
- React Native 지원 불완전
- 2023년 이후 업데이트가 느려 장기 유지보수 불확실

**미채택 사유**
라이브러리 안정성 리스크가 있고 React Native 포팅 구조와 맞지 않는다.

---

## 4. 결과 (Consequences)

### 긍정적 영향
- ✅ 외부 패키지 없이 React 기본 기능만으로 구현 → 번들 크기 최소화
- ✅ `useAuth()` 커스텀 훅으로 로그인·토큰 상태 어느 컴포넌트에서나 접근 가능
- ✅ React Native 포팅 시 동일한 Context 구조 그대로 재사용 가능
- ✅ 구조가 단순해 코드 리뷰 및 Q&A 답변이 용이

### 부정적 영향
- ⚠️ 상태 규모가 커지면 Context 리렌더링 이슈 발생 가능 (현재 규모에서는 무관)
- ⚠️ Redux DevTools 같은 전용 디버깅 도구 없음

### 대응 방안
- Context 리렌더링 이슈 발생 시 `React.memo` 또는 컨텍스트 분리로 대응
- 추후 상태 복잡도가 높아지면 Zustand 마이그레이션 검토 (Context API와 인터페이스 유사)

---

## 5. 검토 일정 (Review)

- **1차 검토:** 3주차 중간발표 시점 (인증 흐름 완성 후)
- **재검토 기준:** 전역 상태 종류가 3개 이상으로 늘어날 경우 Zustand 전환 검토
