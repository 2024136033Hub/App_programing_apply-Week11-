# 발표 Q&A 예상 질문 & 답변

---

## 기획 / 비전

**Q. 한 줄로 이 프로젝트는 무엇인가요?**
> 청각장애인이 수어로 말하면 즉시 한국어 문장으로 변환해주는 AI 번역 플랫폼입니다.

**Q. 누구를 위한 앱인가요?**
> 주 사용자는 청각장애인 본인이고, 보조 사용자는 수어를 모르는 일반인입니다.

**Q. 비슷한 서비스가 있을 텐데 차별점은 무엇인가요?**
> 한국어 수어(KSL) 전용 AI 서비스가 거의 없습니다. 영어 수어(ASL) 기반 서비스는 있지만 KSL은 다른 언어입니다. 국립국어원 통합수어정보 API와 연동해 3,753개 수어 단어를 지원하는 점이 차별점입니다.

**Q. 앱 이름 '수다(手多)'는 무슨 뜻인가요?**
> 수어(手語)의 '수(手, 손)'와 '많다·모두'를 뜻하는 '다(多)'의 합성어입니다. 동시에 일상에서 쓰는 '수다를 떤다'는 말과 같아서, 청각장애인도 마음껏 수다를 떨 수 있어야 한다는 의미를 담았습니다.

**Q. 왜 청록색을 선택했나요?**
> 단순한 취향이 아닙니다. 세계농인연맹(WFD)이 2023년 공식 채택한 농인 깃발(Sign Union Flag)의 핵심색이 터키색(turquoise)입니다. 수어와 농문화의 세계 공통 상징색이어서 이 색을 선택했고, 채도를 낮춰 눈이 편안하도록 했습니다.

## 기술 선택 (ADR)

**Q. 왜 FastAPI를 선택했나요? Django나 Flask는요?**
> Gemini Python SDK와 완전 호환되고, async/await 비동기 처리로 외부 API 3개를 동시 호출해 응답 속도를 높일 수 있습니다. Django는 풀스택 구조가 무거워 API 서버에 과도하고, Flask는 비동기를 기본 지원하지 않아 미채택했습니다. (ADR-0003 참고)

**Q. 상태 관리는 왜 Redux 안 썼나요?**
> 전역으로 공유해야 하는 상태가 로그인 정보(사용자명, 토큰) 하나뿐입니다. Redux는 Action, Reducer, Store 등 보일러플레이트가 많아 이 규모에서는 오버엔지니어링입니다. React 내장 Context API로 충분했습니다. (ADR-0002 참고)

**Q. Gemini Vision API로 전환한 이유는요?**
> 원래 MediaPipe로 손 관절 좌표를 추출하고 LSTM으로 수어를 분류하려 했습니다. 그런데 한국어 수어(KSL) 공개 학습 데이터가 부족하고, 6주 일정 안에 모델 학습이 불가능했습니다. Gemini Vision API로 전환해 3초마다 웹캠 프레임을 분석하는 방식으로 웹캠 기능을 완성했습니다.

## 아키텍처 / 구조

**Q. 앱의 구조를 설명해주세요.**
> 프론트엔드(React), 백엔드(FastAPI), 데이터베이스(SQLite) 3계층 구조입니다. 프론트는 pages/, components/, contexts/, services/ 로 역할을 분리했고, 백엔드는 routers/, services/, models/ 로 분리했습니다.

**Q. 프론트엔드에서 API 호출은 어디서 하나요?**
> `frontend/src/services/api.js` 파일 하나에서 모든 fetch 요청을 관리합니다. 컴포넌트에서 직접 fetch를 부르지 않고 이 파일의 함수를 호출합니다.

**Q. 인증은 어떻게 구현했나요?**
> 로그인 시 서버가 JWT 토큰을 발급합니다. 이 토큰을 Context API로 전역 관리하고, 인증이 필요한 API 요청(번역 기록 조회 등)에 Authorization 헤더로 전달합니다. 비밀번호는 bcrypt로 해싱해 저장합니다.

## 개발자 기본소양

**Q. 개발 환경 설정은 어떻게 하나요?**
> 백엔드: `pip install -r requirements.txt` 후 `uvicorn app.main:app --reload`
> 프론트엔드: `npm install` 후 `npm run dev`
> 자세한 내용은 docs/setup.md에 명령어 복붙 가능하게 정리했습니다.

**Q. 빌드와 배포는 어떻게 하나요?**
> 프론트엔드 빌드: `npm run build` → dist/ 폴더 생성
> 백엔드 배포: Render (Python 런타임, for_deaf.env 환경변수 설정)
> 프론트엔드 배포: Vercel (VITE_API_URL 환경변수 설정)
> docs/deploy.md에 단계별 가이드 작성.

**Q. 테스트는 어떻게 했나요?**
> pytest로 단위 테스트 11개, 통합 테스트 1개 총 12개를 작성했고, `pytest backend/tests/ -v` 실행 시 12 passed 확인했습니다. 커버리지는 번역 API, 사전 API, 인증 API, 기록 API입니다.

**Q. 보안은 어떻게 챙겼나요?**
> API 키는 for_deaf.env 파일로 분리하고 .gitignore에 포함했습니다. JWT로 API를 보호했고, CORS 허용 출처를 명시했으며, 비밀번호는 bcrypt로 해싱합니다.

## 구현 / 시행착오

**Q. 개발하면서 가장 어려웠던 점은?**
> 세 가지 시행착오가 있었습니다.
> 1. passlib과 bcrypt 호환 문제로 500 에러 발생 → bcrypt 직접 사용으로 전환
> 2. Gemini API 무료 할당량 초과 → 다중 키 순환 로직 + Groq API 폴백 구현
> 3. 국립국어원 수어 영상 서버가 외부에서 차단됨 → 백엔드 미디어 프록시 엔드포인트 구현

**Q. AI가 만든 코드를 본인이 설명할 수 있나요?**
> 네. AI가 초안을 작성하더라도 반드시 한 줄씩 읽고 이해한 후 사용했습니다. AGENTS.md에 AI 생성물 검토 원칙을 명시했고, 보안 관련 코드(JWT, bcrypt)는 직접 검토해 수정했습니다.

**Q. 1주일 더 있다면 무엇을 할 건가요?**
> React Native로 모바일 앱을 포팅하고, 수어 인식 정확도를 70% 이상으로 높이며, 오프라인에서도 기본 기능이 동작하도록 개선하겠습니다.

## AI Agent 활용

**Q. AI Agent를 어떻게 활용했나요?**
> Claude Code를 기획·설계·구현·디버깅·문서화 전 과정에 활용했습니다. /spec → /plan → /impl → /test → /docs 워크플로우로 단계별 진행했습니다.

**Q. 본인만의 기법이 있나요?**
> AUTHORING.2024136033.v1.0.md 파일 하나에 프로젝트 구조, 워크플로우, 코딩 컨벤션, 프롬프트 패턴을 통합했습니다. 새 세션을 시작할 때 이 파일만 참조하면 AI가 즉시 프로젝트 컨텍스트를 파악해 반복 설명 시간을 90% 절감했습니다.

**Q. AI가 틀린 적도 있나요?**
> 있습니다. API 호출 방식이 버전마다 달라 틀린 코드를 제시한 적 있고, 보안 관련 코드에서 시크릿 키를 하드코딩하는 실수도 있었습니다. 이런 경우 직접 공식 문서를 확인하고 수정했습니다. LLM Wiki(docs/llm-wiki.md)에 이런 실패 사례를 기록해 같은 실수를 반복하지 않도록 관리했습니다.
